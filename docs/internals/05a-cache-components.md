# Cache Components

Cache Components (`cacheComponents: true`) is a unified feature that changes
how Next.js renders, caches, and prefetches. This document explains the
system end to end. For the core rendering pipeline shared by all modes, see
[Server Rendering](./04-server-rendering.md).

## What the flag enables

The `cacheComponents` flag gates several interconnected capabilities:

1. **`"use cache"` directive** — Per-function and per-component caching
2. **Multi-phase prerendering** — Prospective + final prerender passes
3. **Resume Data Cache** — A cache layer that persists across render phases
4. **Staged rendering** — Incremental rendering of dynamic requests in stages
5. **Per-segment prefetching** — Individual segment responses instead of
   full-route prefetches
6. **Segment Cache** — A client-side LRU cache keyed by segment, replacing
   the legacy router cache
7. **Instant validation** — Dev-only verification that static shells are
   correct

These features are designed as a system: `"use cache"` produces cacheable
units, the Resume Data Cache stores their results, multi-phase prerendering
warms caches at build time, staged rendering uses caches at request time,
per-segment prefetching makes cache granularity visible to the client, and
the Segment Cache stores prefetched segments on the client.

## `"use cache"` — the directive

### What it does

The `"use cache"` directive marks a function or component whose return value
can be cached across requests. It can appear:

- At the **top of a file** — all exported functions become cacheable
- At the **top of an async function body** — that individual function is
  cacheable

### SWC transform

The `"use cache"` transform lives in
`crates/next-custom-transforms/src/transforms/server_actions.rs` (the same
visitor that handles `"use server"`).

When SWC encounters `"use cache"`, it:

1. **Hoists** the original function as a `_INNER` const:

   ```javascript
   const myFunction_INNER = async function (param1, param2) {
     // ... original function body ...
   }
   ```

2. **Creates a wrapper** that routes through the cache runtime:

   ```javascript
   const myFunction = $$reactCache__(function myFunction() {
     return $$cache__(
       'default', // cache kind
       'a1b2c3d4...', // reference ID (cache key)
       2, // bound args length
       myFunction_INNER, // the original function
       Array.prototype.slice.call(arguments, 0, 2) // captured arguments
     )
   })
   ```

3. **Exports** the wrapper as the public identifier

At runtime: call `myFunction` -> `$$reactCache__()` -> `$$cache__()` ->
`myFunction_INNER` (on cache miss).

Note: The wrapper is a non-async named function (not `async function(...args)`).
Arguments are captured via `Array.prototype.slice.call(arguments)` rather
than a literal array.

### Cache key derivation

Cache keys are generated by `generate_server_reference_id()` in
`server_actions.rs`:

1. Compute `SHA1(hash_salt + file_name + ':' + export_name)`
2. Prepend a metadata byte encoding:
   - Bit 7: type (1 = cache directive, 0 = server action)
   - Bits 6-1: argument mask (which of the first 6 args are used)
   - Bit 0: rest arguments indicator
3. Hex-encode the result

The metadata byte lets the runtime distinguish cache directives from server
actions and handle argument binding correctly.

## Resume Data Cache

The Resume Data Cache is the persistence layer for `"use cache"` results.

**Defined in**: `packages/next/src/server/resume-data-cache/resume-data-cache.ts`

### Two interfaces

```typescript
// Mutable — used during prerendering to fill the cache
interface PrerenderResumeDataCache {
  readonly cache: UseCacheCacheStore           // "use cache" results
  readonly fetch: FetchCacheStore              // Cached fetch responses
  readonly encryptedBoundArgs: EncryptedBoundArgsCacheStore  // Encrypted bound args
  readonly decryptedBoundArgs: DecryptedBoundArgsCacheStore  // In-memory only
}

// Immutable — used during rendering to read from the cache
// Uses Omit<Store, 'set'> to enforce immutability — same fields, read-only
interface RenderResumeDataCache { ... }
```

Each store type is a specialized Map (not generic `Map<string, any>`).

### Lifecycle

1. **Phase 1 (prospective prerender)**: A `PrerenderResumeDataCache` is
   created. As `"use cache"` functions execute, their results are stored
   in the mutable cache.

2. **Serialization**: The cache is serialized via `stringifyResumeDataCache()`
   — Maps become JSON objects, compressed with zlib, and base64-encoded.
   The `decryptedBoundArgs` store is intentionally **not persisted**.

3. **Phase 2 (final prerender)**: The serialized cache is deserialized into
   a `RenderResumeDataCache` via `createRenderResumeDataCache()`. Cached
   results are returned immediately without re-executing the functions.

4. **Request time**: The same serialized cache from the build is loaded as a
   `RenderResumeDataCache`. Cache hits bypass function execution; misses
   execute the function fresh. Invalidation is based on `revalidate` times
   and tags.

## Multi-phase prerendering

Without Cache Components, prerendering is a single pass that bails on
dynamic API access. With Cache Components, prerendering runs in two phases.

### Phase 1: Prospective prerender

The work unit store type is `'prerender'`. Dynamic APIs like `cookies()`
return **hanging promises** instead of throwing or postponing — the render
continues past dynamic access points so that `"use cache"` functions
deeper in the tree can still execute and warm the cache.

```
Create PrerenderResumeDataCache (empty)
Create CacheSignal (tracks outstanding cache reads)
Run createComponentTree() → produces CacheNodeSeedData
  → "use cache" functions execute, filling the cache
  → Dynamic API access returns hanging promises (never resolves)
  → CacheSignal.beginRead()/endRead() track each cache read
  → CacheSignal.cacheReady() resolves when all reads settle
Abort the render → output is discarded, purpose was to warm caches
```

See [Prerendering — CacheSignal](./05-prerendering.md#cachesignal--tracking-cache-reads)
for how `CacheSignal` determines when cache warming is complete.

### Phase 2: Final prerender

The work unit store type is still `'prerender'`, but now with a
`RenderResumeDataCache` filled from phase 1. The render is aborted
after a single React task via the `controller` on the store — this
prevents the render from reaching dynamic code paths.

```
Deserialize phase 1 cache → RenderResumeDataCache
Run createComponentTree() again
  → "use cache" results served from cache (no re-execution)
  → Abort after a single React task (avoids dynamic code paths)
Output is the actual static shell
```

After the final prerender, `dynamicTracking` determines whether the page
has a static shell (PPR), which segments need request-time rendering, and
the postponed state format. See
[Prerendering — DynamicTrackingState](./05-prerendering.md#dynamictrackingstate)
for how dynamic access is recorded.

See [Prerendering](./05-prerendering.md) for the full prerendering pipeline
including PPR and postponed state.

## Staged rendering

For **dynamic requests** (not prerendering), rendering happens in stages.
This enables the server to produce partial responses incrementally.

### The stages

```
Before → EarlyStatic → Static → EarlyRuntime → Runtime → Dynamic → Abandoned
```

| Stage        | What renders                                                          | Sync IO allowed? |
| ------------ | --------------------------------------------------------------------- | ---------------- |
| Before       | Nothing yet                                                           | N/A              |
| EarlyStatic  | Runtime-prefetchable segments render immediately; others are deferred | No               |
| Static       | Deferred (non-prefetchable) segments now render                       | No               |
| EarlyRuntime | Runtime-prefetchable segment output resolves                          | No               |
| Runtime      | Non-prefetchable segment output resolves                              | Yes              |
| Dynamic      | Full dynamic rendering                                                | Yes              |
| Abandoned    | Terminal — render will be restarted                                   | N/A              |

### `StagedRenderingController`

Defined in `packages/next/src/server/app-render/staged-rendering.ts`. The
controller manages promise-based gates between stages.

**Key API:**

- `advanceStage(stage)` — Advances to the target stage, resolving all
  intermediate stage promises and firing their `onStage` listeners.
  Records `staticStageEndTime` and `runtimeStageEndTime` timestamps at
  the corresponding transitions.

- `waitForStage(stage)` / `delayUntilStage(stage, name, value)` — Returns
  a Promise that resolves when the render reaches the given stage.
  Components use this to defer their output until the appropriate stage.

- `onStage(stage, callback)` — Registers a callback to fire when a stage
  is reached. If the stage has already been reached, fires immediately.

- `abandonRender()` — Resolves intermediate stages (so caches can fill)
  then marks the render as `Abandoned`. Triggered by cache misses or sync
  IO errors during abandonable renders.

- `syncInterruptCurrentStageWithReason(error)` — Called when sync IO occurs
  during a stage that doesn't allow it. Depending on the render type, this
  either abandons the render, captures the error and jumps to Dynamic, or
  sets the interrupt reason for the caller to handle.

### How segments are deferred

In `create-component-tree.tsx`, segments are deferred based on their
prefetchability:

```typescript
// Runtime-prefetchable segments render immediately (no deferral)

// Non-prefetchable segments wait for the Static stage
if (!isRuntimePrefetchable) {
  await stagedRendering.waitForStage(RenderStage.Static)
}
```

### Static stage byte length

The RSC payload includes a `staticStageByteLengthPromise` (the `l` field in
`InitialRSCPayload`). This resolves to the byte offset where the static
stage ends in the Flight stream. The client uses this to split the response
into cacheable (static) and non-cacheable (dynamic) portions.

## Per-segment prefetching

At build time, `collectSegmentData()` in `collect-segment-data.tsx`
post-processes the full-page Flight response into individual per-segment
prefetch buffers:

```
Full page Flight response
         │
    collectSegmentData()
         │
    For each segment in the FlightRouterState tree:
      Extract its CacheNodeSeedData
      Re-serialize as a standalone Flight response
      Store as a .segment.rsc file
```

At request time (for dynamic pages with Cache Components), per-segment
responses are generated on the fly using the same mechanism.

Each segment's Flight data includes its CSS `<link>`/`<style>` elements —
they're part of the `rsc` ReactNode in `CacheNodeSeedData`.

## Segment Cache (client)

The Segment Cache (`packages/next/src/client/components/segment-cache/`)
replaces the legacy router cache when per-segment prefetching is supported
(`S: true` in the RSC payload, where `S` reflects
`workStore.isStaticGeneration || ctx.renderOpts.cacheComponents` — meaning
Cache Components always enables per-segment prefetching, even for dynamic
pages).

### Architecture

The cache is an LRU cache keyed by a `RouteCacheKey` (pathname + search +
nextUrl) at the route level, with individual segments keyed by their
segment path within each route.

```
RouteCacheKey (pathname + search + nextUrl)
  └── RouteTree (tree structure describing available segments)
        └── SegmentCacheEntry per segment (keyed by segment path + params)
```

### Prefetch flow

1. **`<Link>` enters viewport** → `prefetch()` in `prefetch.ts` creates a
   `RouteCacheKey` and schedules a `PrefetchTask`

2. **Route tree fetch** → The scheduler fetches the route's tree prefetch
   metadata (`.prefetch.rsc`), which describes the segment tree shape,
   available segments, stale times, and prefetch hints

3. **Per-segment fetch** → For each segment in the tree, the scheduler
   fetches its individual prefetch response. Segments are fetched with
   a priority system:
   - `Intent` (priority 2): The most recently hovered/touched link
   - `Default` (priority 1): Standard viewport-triggered prefetches
   - `Background` (priority 0): Revalidation of partially cached entries

4. **Cache storage** → Each segment's Flight data is stored independently

### Navigation flow

When the user navigates (`navigate()` in `navigation.ts`):

1. Look up the `RouteCacheKey` in the cache
2. Walk the route tree, assembling cached segments into a response
3. For segments that are cached: use immediately (synchronous navigation)
4. For segments that are missing or stale: fetch from the server
5. React reconciles the assembled tree with the existing DOM

This enables **synchronous navigations** when all segments are cached —
the function returns an immediate result instead of a Promise.

### Differences from legacy router cache

|               | Legacy router cache             | Segment Cache                              |
| ------------- | ------------------------------- | ------------------------------------------ |
| Granularity   | Full route                      | Per segment                                |
| Prefetch unit | Route up to first `loading.tsx` | Individual segments                        |
| Cache key     | URL                             | Pathname + search + nextUrl + segment path |
| Invalidation  | Route-level                     | Per-segment stale times                    |
| Navigation    | Always async (fetch)            | Sync when cached                           |

## Instant validation

In development, instant validation checks that the static shell produced
during prerendering matches what would be rendered at request time. This
catches bugs where cached output diverges from fresh output.

### How it works

1. **Boundary placement** — `PlaceValidationBoundaryBelowThisLevel` (in
   `server/app-render/instant-validation/boundary-impl.tsx`) and
   `RenderValidationBoundaryAtThisLevel` (in
   `client/components/instant-validation/boundary.tsx`) are context-based
   components. `LayoutRouter` conditionally wraps segment content with
   `RenderValidationBoundaryAtThisLevel` when a boundary ID is provided
   via context.

2. **ID tracking** — Each `InstantValidationBoundary` calls
   `state.renderedIds.add(id)` when it renders, building a Set of
   boundary IDs that actually appeared in the static shell.

3. **Validation** — `spawnStaticShellValidationInDevImpl()` in
   `app-render.tsx` runs a warmup render, collects rendered boundary IDs,
   then compares them against expected segments from the
   `unstable_instant` config.

4. **On failure** — Validation errors are logged to the CLI and sent to
   the browser via the RSC stream.

### Configuration

Validation is driven by the `unstable_instant` segment config property on
layouts and pages. It supports granular disable flags:
`unstable_disableValidation`, `unstable_disableDevValidation`, and
`unstable_disableBuildValidation`.

The validation boundary components are dead-code-eliminated from browser
bundles via a `typeof window === 'undefined'` guard in the client-side
facade (`client/components/instant-validation/boundary.tsx`).
